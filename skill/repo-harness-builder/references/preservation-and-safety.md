# Preservation And Safety

## The Whole Model

For a new or effectively empty repository, the harness creates the complete useful baseline after plan approval, including `README.md`. For an existing repository, preservation means informed approved evolution: analyze relevant content, reuse what is sound, and propose concrete improvements or additions.

Never overwrite or archive existing content without explicit approval. When content is obsolete, structurally incompatible, or the user prefers a reset, offer a distinct conversational choice to archive the superseded content and start from a clean generated baseline. Only after that choice is resolved should the builder form the deterministic content-bound apply plan. Apply requires its digest and refuses when the current plan differs.

## Default Evidence

Scope planning evidence to intended write paths, relevant existing ancestors, and canonical renderer inputs. A full-tree strict snapshot may be used when requested, but is not the default.

## Classification

| Target | Result |
|---|---|
| Absent | Create it |
| Present with exactly the rendered bytes | Already identical; nothing to do |
| Present with useful content | Analyze it and propose an integrated update |
| Present but obsolete or incompatible | Offer archive and clean-baseline generation separately |
| Selected root pointer missing its exact directive | Append only the smallest newline-delimited directive |
| Selected root pointer already containing its exact directive | Leave every byte unchanged |
| Root `.gitignore` missing exact `.codegraph/` with default enabled | Create it or append only that directive; preserve all existing bytes and line endings |
| `--no-codegraph-ignore` selected | Record `project.ignoreCodegraph: false`; do not create or edit `.gitignore` |
| Present as a directory or indirect target | Refuse apply before creating anything |

Root pointer detection matches the exact directive as a complete line. Substrings, comments, prefixes, suffixes, and near-matches do not count. Append preserves every existing byte, uses the file's consistent CRLF convention when present, otherwise uses LF, and adds only the separator needed plus the directive and its terminating newline.

The same byte-preserving integration applies narrowly to root `.gitignore`. Default render records `project.ignoreCodegraph: true` and manages exactly one line, `.codegraph/`. `--no-codegraph-ignore` records false and omits `.gitignore` entirely. `check` reads that manifest boolean so an explicit opt-out is never reinterpreted. The builder never creates or writes anything inside `.codegraph/` and manages no other ignore rule.

## Prior-Version Upgrades

Audit installed manifest data, generated markers, managed files, and runtime projections before planning. Use `current` for exact rendered bytes, `stale` for current-generator drift, `missing` for absent paths, `human-evolved` for structurally valid human-owned changes, and `legacy` only when older repo-harness-builder provenance is proven. Unknown provenance is never enough to claim generated ownership.

Upgrade analysis returns proposals with no replacement, archive, or deletion apply actions. A proven generated `stale` or `legacy` file may receive a replace-or-keep proposal. A `human-evolved` file receives integrate, archive/start-clean, or keep choices. The user must explicitly approve the exact mutation later in the content-bound plan. Never silently delete.

The fixed generated-skill transition is the sole bounded exception. Migration authority requires the installed manifest to declare the exact three legacy harness skills and every exact manifest-owned source to match deterministic generated bytes. Normal render preview may then emit one `migrate-generated-skills` action bound to source, destination, manifest, checker, and removal digests. Unrelated `{project_id}-*` skills are human-owned unless their exact paths are declared by that validated manifest and their bytes match exactly. Prefixes, directory scans, and similar names never grant replacement or removal authority.

## Adding A Runtime Later

`.repo-harness/manifest.json` and `.repo-harness/check.py` are generated files like any other, so a second run classifies them as present and leaves them untouched. Widening the runtime set therefore creates the new wrappers and projections correctly while the manifest keeps recording the old set, and the generated checker goes blind to everything the manifest does not list. It reports `current` after inspecting only part of the harness, which is worse than reporting drift.

The plan and the check both carry `runtimeSet` with `recorded`, `requested`, and `matches`, plus `unrecorded` and `staleManifest` only when the requested set names a runtime the manifest never recorded. That is the one direction needing recovery. Requesting fewer runtimes than recorded creates nothing new and leaves the checker covering everything, so report the difference and say no recovery applies. Surface the recovery case before approval and name it: delete the two files in `staleManifest`, then run again with the complete set. The builder recreates them because they are then absent, and no existing byte is replaced. This keeps additive-create intact rather than teaching the renderer to overwrite.

`CHANGELOG.md` needs no special case. If it exists, it is left alone like anything else. If it is absent, the standard dated changelog is created.

Root `README.md` is part of the complete baseline for a new or effectively empty repository. In an existing repository, read and analyze the README, then propose an informed update that preserves useful project-specific content and improves gaps. Generated ownership markers may bound generated material, but they never justify refusing analysis or improvement. If integration is unsuitable, offer archive and start-clean as a distinct conversational choice. This choice must not require `APROBAR`; exact uppercase approval remains exclusive to the builder's content-bound apply plan. Never mutate or archive the README until the user approves the exact proposed action.

README language selectors are atomic across peers. If an existing `README.md` does not already link reciprocally to `README.es.md`, the ordinary additive writer cannot complete that integration. Remove `README.es.md` from `create`, report it in `blocked` with the required `README.md` integration, and refuse the entire apply. Do not create a one-way Spanish peer or report bilingual completeness. A future bounded existing-file integration executor may resolve this broader pending capability after TDD and exact approval.

## Human-Owned Versus Generated

After creation, two kinds of file behave differently under `check`:

- **Generated**: canonical skills, runtime projections, wrappers, and the manifest. Compared byte for byte. A difference is reported as `modified`.
- **Human-owned**: root `README.md`, `.gitignore`, the rulebook, `CHANGELOG.md`, and everything under `docs/repo-harness/`. `.gitignore` keeps every existing byte and only receives the exact approved `.codegraph/` append. Other human-owned files are compared by the sections they promise. This tolerance supports project-specific evolution; it does not freeze content or remove the builder's duty to analyze and propose improvements.

This is the distinction that keeps the check useful. Comparing a rulebook by content would flag every real project as broken on day one.

## Approval

After conversational repository-shape and integration choices are resolved, show all four action sets and the current content-bound apply plan digest. When the create set is grouped or counted for the human, attribute each root pointer to the runtime that requires it, never with the common core. `CLAUDE.md` counts toward `claude-code`; `AGENTS.md` counts toward `opencode` or `pi`, and a combination selecting both counts the one shared file once. Only `REPO-HARNESS.md` and `CHANGELOG.md` are common. A summary that inflates the common count understates what each profile costs. Before asking, state `Answers are case-sensitive and must be written exactly in uppercase.` Then show exactly `APROBAR` and `DENEGAR`. Only exact `APROBAR` permits writing; exact `DENEGAR` stops. Reject every other answer with `Invalid answer. Write exactly APROBAR or DENEGAR in uppercase.` Never normalize an answer or reuse an earlier preview digest. Apply requires the approved current digest and fails closed when pointer bytes or another planned target changed. Approval of repository writes never approves Git, provider, backup, or publication actions.

## Containment And Its Honest Limit

Reject unsafe relative paths, absolute paths, parent traversal, invalid existing targets, and indirect existing ancestors before any write. Apply the same ancestor guard before every check read. After each create, confirm the resolved path is still inside the selected root and remove it if it is not.

This is proportional containment for a cooperative working copy. It is not a security boundary against an attacker who can replace directories underneath a running process. Version control is the real safety net, and the tool says so rather than implying a guarantee it does not provide.

## Failure Behavior

Refuse indirect targets and unsafe paths. Verify created bytes, pointer result digests, and links after writing. On failure, remove only files this run created and only when their bytes still match what this run wrote. The bounded generated-skill migration additionally restores exact source, manifest, checker, and appended bytes and removes fixed destinations if any migration or additive continuation phase fails. Never replace or delete other pre-existing content.

## Generated Checker Boundary

The generated checker trusts no mutable manifest field until the exact manifest bytes match its embedded SHA-256. It then requires the exact checker schema, an `integrationMode` of `integrated` or `standalone`, supported runtimes, safe canonical skill names, and repository-relative paths. It rejects absolute, drive-qualified, parent-traversing, symlinked, reparse-point, and outside-resolving paths before content reads. Its scope remains manifest integrity and canonical runtime skill projections only.
