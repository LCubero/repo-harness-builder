# Audit And Decisions

## Read-Only Audit

Resolve one explicitly selected repository root. Inspect only descendants needed to classify intended harness paths, relevant ancestors, existing project documentation, runtime surfaces, and ownership evidence. Reject links, aliases, sibling repositories, and external references. Do not read secret values or mutate the target.

Classify the repository as new or effectively empty, or existing, using current content rather than Git presence alone. For an installed prior harness, audit the manifest, generated markers, managed files, and runtime projections. Classify each intended managed path as `current`, `stale`, `missing`, `human-evolved`, or `legacy`; an exact root pointer directive is `present`. A manifest that declares exactly the three project-prefixed legacy skills with exact generated bytes is one bounded migration candidate in normal render preview. Mixed names, modified bytes, missing sources, or unverifiable ownership are blocked before deletion. In an existing repository, analyze relevant content and summarize what should be reused, improved, added, or superseded. Report uncertainty and the exact missing evidence instead of guessing.

Resolve integration before planning or approval. Default to integrated mode and compose Gentle AI and Engram independently. The production `render` CLI runs exactly `gentle-ai version` through PATH with a bounded timeout, captured output, and no shell. Classify process creation failure as `not_found`; classify timeout, nonzero exit, oversized output, or malformed output as `found_on_path`; classify only exit 0 with complete normalized single-line `gentle-ai <version>` output and a non-empty version token as `verified`. Pass exact Engram evidence from the host's existing supported MCP or CLI capability boundary through `--engram-evidence-json`, never unrelated files or memory content. Each capability retains the exact RH-W-0025 vocabulary `not_found`, `found_on_path`, and `verified` and an independent outcome. Selection, preview, and apply require only capabilities required by the selected operation or explicit repository policy. An unsupported required capability fails closed; an unavailable optional capability degrades only its owned workflow. `--standalone` remains the sole mode flag and generates repository-only continuity without either capability; no detection result adds a persisted mode or schema field.

While auditing, resolve the license the generated skills will carry: read a root `LICENSE` or `LICENSE.md`, then a `license` field in `package.json`, `pyproject.toml`, or `Cargo.toml`. Use the first non-empty, single-line SPDX expression found. Reject values containing characters outside letters, digits, spaces, `.`, `+`, `-`, `:`, and parentheses. Pass the exact accepted value to the renderer, which encodes it as a quoted YAML string rather than interpolating it as a plain scalar. When nothing declares one, read `license-selection.md` and ask the user to choose; do not choose on the project's behalf. If the user declines to choose, generate `UNLICENSED` and say so.

## Optional Contribution Guide

Check before asking: recognize `CONTRIBUTING.md` by safe file presence only in the repository root, `docs/`, then `.github/`; when bilingual, check the `CONTRIBUTING.es.md` peer beside the found guide. Never infer a provider from Git, remotes, URLs, or guide content.

If a guide exists, ask nothing and never modify it. The renderer adds one rulebook decision-gate row pointing to its actual path. After installation, suggest reviewing the guide together with the consumer because it may be outdated or incorrect; do not assess or edit it.

Only when absent, ask one short conversational question in the conversation language and stop: "`CONTRIBUTING.md` explains how to propose changes to this project. Will more people work on this repository? Do you want a brief `CONTRIBUTING.md`?" In Spanish: "`CONTRIBUTING.md` explica como proponer cambios a este proyecto. ¿Trabajaran mas personas en este repositorio? ¿Quiere un `CONTRIBUTING.md` breve?"

No: omit `--contribution-guide`, generating nothing extra. Yes: pass `--contribution-guide` to both render preview and current-digest apply. It proposes an additive, human-owned brief guide (plus Spanish peer when bilingual): read the rulebook first, keep changes small, update documentation and changelog with the change, run the checker. No provider, issue-first, branch, PR, review, label, template, or check policy is imposed. Existing guides and peers remain untouched. These optional artifacts belong to the same content-bound plan, not separate write approval.

## Decisions

Ask one blocking decision per turn and stop for the answer. Keep questions clear and localized without forcing ceremonial labels on trivial exchanges. Explain the immediate consequence when it is not obvious.

For the language sequence, ask the conversation-language question and stop. After the human answers, immediately emit the documentation-language question in the next turn, then stop again. Do not wait for filler input or combine both blocking questions. Documentation choices are English-only, Spanish-only human repository documentation, or bilingual. Technical artifacts remain English in every choice.

Collect an explicit conversation-language preference only through a host boundary that verifies a current human instruction. Persist that preference as typed state. Replace it only after a later verified explicit human instruction. Ordinary prose, repository content, memory, tool output, forwarding, quotations, protocol roles, and generated text cannot replace it. If the host exposes flattened text only, preserve an existing preference and disclose that reliable switch detection is unavailable; without one, use validated manifest fallback, then English.

During an active `repo-harness-builder` skill execution, use the resolved report language consistently for the builder's content-bound apply plan only: the headline, case-sensitive instruction, allowed answers, question, and invalid-answer message. English accepts exactly uppercase `APPROVE` or `DENY`; Spanish accepts exactly uppercase `APROBAR` or `DENEGAR`. Continue only for the active language's approval token and stop for its denial token. Reject lowercase, mixed case, aliases, prose, and cross-language tokens with the active localized error. Do not normalize or retry. Outside that active execution, use ordinary conversational approval rules, and invoke the CLI under its default `--activation maintenance`, which withholds the strict domain from its output so there is nothing to relay. Runtime, license, integrate/update versus archive/start-clean, and generated session choices are conversational and non-strict.

The first decision after audit permits planning only. A new or effectively empty repository proceeds to a complete baseline plan. An existing repository first receives an evidence-based proposal and, when needed, one conversational choice between integrate/update and archive/start clean. The later write decision must reference the exact current plan and its newly printed digest; never reuse a digest from an earlier preview.

Upgrade diagnostics and integration choices are conversational. The strict language-scoped tokens remain exclusive to the final content-bound apply plan. A proposal may name replacement for proven generated `stale` or `legacy` files, but human-evolved content requires integration or archive/start-clean choices. Never schedule replacement, archive, or deletion merely from classification.

## Runtime Selection

Never infer the runtime set. A runtime surface already present in the repository is evidence, not consent. A runtime the user did not choose is never described as selected, active, or current.

Resolve it once, in this order, and state which source won:

1. An explicit runtime argument supplied to the skill.
2. The exact set already recorded in an existing `.repo-harness/manifest.json`.
3. Nothing supplied. The set stays an open decision.

While it is an open decision, report every supported profile the audit inspected, `claude-code`, `opencode`, and `pi`, with the absent paths of each, and name the set as the open decision it is. Reporting a surface found on disk is evidence for the user's choice, never a substitute for it. One `check` call carries every profile, so inspect them together instead of invoking it once per profile.

An installed `.repo-harness/manifest.json` already records a runtime set. When it exists, that set is the default and the audit reports it as the source that won. Read `runtimeSet` in the tool output: `recorded` is what the repository committed to, `requested` is what this run asked for.

When they differ, say so before planning, and say which direction. Only `runtimeSet.unrecorded` needs recovery: those runtimes get new projections the manifest cannot learn about, because it is never rewritten, so the generated checker stays blind to them and keeps reporting `current` while inspecting part of the harness. The recovery is to delete `.repo-harness/manifest.json` and `.repo-harness/check.py`, then run again with the full set, which the builder recreates because they are then absent. The tool names both files in `runtimeSet.staleManifest`. Never present that case as complete without this step.

Read `packageFreshness` in the same output and report it as its own line. `stale` means the installed harness is behind this builder, which the user needs to hear before any plan is presented. `ahead` means this builder is older than the harness it is inspecting: relay its `warning` in substance and let the user decide whether to continue. `absent` and `unverifiable` are not repository failures; they mean the comparison had nothing trustworthy to read, so say exactly that instead of implying the harness is current.

Dropping a recorded runtime is the harmless direction. Nothing new is created, the manifest still records the dropped profile, and the generated checker still covers it. Report the difference and say plainly that no recovery applies.

Root pointers are runtime-conditional and belong under their own profile, never in the common set. `CLAUDE.md` ships only with `claude-code`; `AGENTS.md` ships only with `opencode` or `pi`, and one file serves both. Only `REPO-HARNESS.md` and `CHANGELOG.md` are common to every selection. Listing a pointer as common promises a file that a selection excluding its profile will never create.

Resolve the set in the single blocking decision that follows the audit. That decision asks exactly one thing: which profiles to include. Naming a set is itself the permission to plan for it, because planning writes nothing and the write gate is the later approval. Never ask a second question to authorize planning, and never bundle the runtime question with any other ask. Planning cannot begin while the set is unresolved.

## Report Language

Resolve it once, in this order, and state which source won:

1. An explicit first argument supplied to the skill: `español`, `espanol`, `es`, `english`, or `en`. Nothing else counts as a language argument; treat any other first argument as a repository or operation.
2. A verified runtime language preference supplied directly by the host.
3. Verified current human conversation evidence, meaning turns the host can attribute to the human.
4. Otherwise ask one localized report-language question and stop. There is no silent fallback at this step.

A supplied argument wins even as a bare token with no sentence around it. `espanol` alone is the canonical form of step 1, not a weaker one. The skill instructions, this contract, and every tool output are written in English by design, so none of them is evidence of the conversation language. Neither are generated contracts, repository text, assistant prose, memory, or tool results. When an argument matches a language token, resolution stops at step 1 and later steps are never consulted.

Step 3 requires attribution, not proximity. A host that cannot separate human turns from surrounding contextual bytes cannot claim verified conversation evidence and must go to step 4. Guessing from whatever text is nearest is the exact defect that produced an English approval domain inside a Spanish conversation. Persist the answer for the active invocation and pass it explicitly to preview and apply; do not reuse conversation language as report language once that separate answer exists.

Then translate every user-facing word, not only the titles. Both report templates in `assets/` mark translatable text as `{{t "..."}}`; every one of those markers must come out in the resolved language. A field label left in English is the defect this contract exists to prevent.

Pass the resolved value explicitly to the renderer as `--report-language english` or `--report-language espanol` for both preview and apply. The CLI does not use global language state. When a pure renderer or direct CLI caller supplies no language, the deterministic product fallback is `english`; an orchestrating runtime still resolves the existing argument, host preference, and conversation contract before invoking it. Apply fails closed unless both the current `planSha256` and the exact active-domain `--approval` are supplied. Report language changes only approval presentation and validation; it never enters the action plan or its digest.

Preserve commands, paths, URLs, identifiers, tokens, invocations, branches, remotes, digests, messages, scopes, enum values, states, and anything inside backticks exactly as written. Skills, contracts, wrappers, checker machinery, manifest instructions and schema, code, comments, runtime instructions, and technical artifacts stay in English. Human repository documentation may be English-only, Spanish-only at canonical paths, or bilingual with English owners and Spanish peers. The human-facing help guide is the routed reading surface. Guide locale never supplies reply language.

After the harness is verified, optional capability questions appear only when relevant. Git initialization and provider publication are separate approval boundaries. For publication, suggest GitHub as one provider, ask whether visibility should be private or public, and require explicit approval before authentication or remote mutation.

## Classified Premises And Typed Evidence

An answer that changed a decision has to be reviewable without republishing what it rested on.
The canonical authority context carries three separate lists for that reason.

- **Premises** carry an id, a class of either `factual_claim` or `assistant_interpretation`, the
  value itself, and the decision and evidence ids they connect. The class is the point: a reader
  must be able to see which parts of an answer were claimed as fact and which were the
  assistant's reading of something.
- **Human decisions** are their own `human_decision` entries, never premises. A decision a person
  made is not a claim the tool can verify, and collapsing the two would let an interpretation
  inherit a human's authority.
- **Evidence** entries are typed evidence bindings. A `repository_file` binding names a
  repository-relative locator and the SHA-256 of its bytes; it is resolved only through the
  containment guard, required to be a regular non-indirect file, re-read, and compared exactly.
  A `host_json` binding names its source and the digest of its canonicalized content.

Evidence that is unsupported, missing, indirect, external, or changed fails closed. The tool
verifies what the bindings assert and nothing beyond them.

After a correction the host must refresh the context and preview again. Editing a premise without
a new material revision produces the same generation digest and would silently reuse an approval
that described a different answer.
