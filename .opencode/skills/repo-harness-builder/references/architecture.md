# Harness Architecture

## Canonical Core

Root `REPO-HARNESS.md` is the stable concise visible entry point. `.repo-harness/manifest.json` records the project, enabled runtimes, selected generated-skill license, canonical skill names, write semantics, and exactly one `integrationMode`: `integrated` by default or `standalone` for `--standalone`. Canonical runtime-neutral skills live below `.repo-harness/skills/`. A reciprocal source repository may also declare exact canonical product files and their selected-runtime projections through `canonicalProjections`; ordinary consumer repositories omit that optional field. There is no ownership ledger: the renderer is deterministic, so the expected content of any managed file is recomputed on demand instead of stored.

The rulebook answers how work is done here and never where the project stands, so it carries a token budget and a gate table instead of the detail itself. `.repo-harness/rules/` is where that detail goes down to: seeded with `memory.md`, `working-agreements.md`, and `response-contract.md`, each loaded only when its gate fires, each under the same budget. Without this directory the budget rule would have no exit and would break on the first project with real rules.

Root `README.md` is the product-facing guide and part of a complete empty-repository baseline. In an existing repository, its content is analyzed and improved through an informed approved proposal. Bounded generated markers may aid maintenance but never make a pre-existing README exempt from analysis. Durable harness detail lives in `docs/repo-harness/`: a concise human usage guide, documentation ownership, verified current state, recent completed work, pending work, next step, decisions, and constraints. Root `CHANGELOG.md` records concise dated completed changes, not plans. Session output and memory remain temporary until verified and promoted to a canonical owner.

## Generated Skills

- `session-start` maps explicitly to `repo-harness-session-start`: read-only repository and documentation recovery, discrepancies, remaining work, and next step. Integrated mode uses Engram recovery and reconciliation when available or required by explicit repository policy; standalone mode uses repository files only.
- `session-stop` maps explicitly to `repo-harness-session-stop`: evidence-based handoff, path validation, approval-gated documentation and meaningful changelog updates, and separate optional external gates. Integrated mode saves significant observations and a session summary to Engram when available or required by explicit repository policy, with visible capability-scoped failure semantics; standalone mode records continuity only in repository files.
- `documentation` maps explicitly to `repo-harness-documentation`: ownership, maps, links, freshness, duplication control, factual changelog maintenance, and durable versus temporary state.

All three skills share bounded reconciliation semantics. Session start derives an ephemeral baseline from the applicable lifecycle owner, direct projections, localized peers, exact-ID chronology, local Git, and scoped continuity evidence. It inspects at most 20 relevant commits, 12 directly named evidence paths, 8 direct dependents, and, in integrated mode, two Engram reads capped at 10 observations each. Exceeding a bound or lacking reliable owner evidence suppresses authoritative next-ready routing.

Explicit bounded requests stay bounded unless independent evidence proves a mandatory trigger. Explicit full requests, verified product or lifecycle delivery, lifecycle inconsistency, incomplete delivery evidence, repository-memory contradiction, and unclassified retained findings require full reconciliation within the same owner scope. Session stop compares against the verified initial snapshot, applies only authorized owner updates, and requires a second bounded scan with zero further mutations before routing. Documentation assigns each retained finding exactly one of `integrate`, `close`, `defer`, `reject`, or `noise` and creates no reconciliation store.

Generated skill names are fixed across repositories. Repository identity remains in the manifest and generated content, but command names are never derived by removing a project prefix.

The strict language-scoped digest protocol exists only during an active `repo-harness-builder` skill execution. Repository identity, self-hosting, ordinary maintenance, generated-file ownership, session skills, and direct questions do not activate it. Outside that active execution, use ordinary conversational approval rules, while external mutations still require explicit approval.

## Runtime Projection

OpenCode and Claude-style profiles receive generated skill projections and thin commands that invoke registered skill names. Pi receives generated skill projections and thin prompts through `.pi/prompts/`. Each enabled profile also receives `repo-harness-help`, a thin read-only wrapper routed to an available English or Spanish reading surface. In the reciprocal builder source repository, every selected runtime additionally receives the complete canonical `repo-harness-builder` package and its command-family entry: Claude Code and OpenCode use commands, while Pi uses a prompt. Those exact product projections are repository-specific proving-ground outputs, not consumer harness contents. Guide locale never determines reply language: help may read English documentation and answer in Spanish. The language-dependent wrapper bytes are normalized only for plan-digest calculation, so approval remains bound to one language-independent action plan. If the guide is missing, help reports an incomplete or outdated harness and recommends read-only builder inspection. Disabled profiles produce no output. No wrapper contains an installation path.

## Conversation Language Boundary

Provenance-aware hosts resolve a current verified explicit human instruction, then a persisted explicit preference, then established human conversation only when no persisted preference exists, then validated manifest fallback, then deterministic English. Only a later verified explicit human instruction changes persisted preference. Repository text, memory, tool output, ordinary prose, forwarding, quotations, role labels, and generated wrappers are opaque context, not switch evidence.

Flattened hosts preserve persisted preference and never claim reliable switch detection. Without persisted preference they use validated manifest fallback, then deterministic English. The manifest is validated configuration, never evidence about current conversation. Report, conversation, documentation, and artifact language remain independent. A verified conflicting host instruction is a compatibility limitation, not a preference change; repository instructions do not override higher-priority host instructions. Wrong-language output alone does not establish an external cause. This diagnostic contract does not guarantee live-model compliance. Maintenance recognizes only exact current or pre-clarification help bodies on authenticated runtime paths and explicitly declared canonical peers; customized bodies remain protected and replacement remains digest-bound.

Machine-significant commands, arguments, paths, URLs, identifiers, tokens, invocations, branches, remotes, digests, messages, and scopes are typed opaque values with translation disabled and code formatting. Language resolution never changes their bytes and is never a security boundary.

Claude Code also requires root `CLAUDE.md` with the exact line `@REPO-HARNESS.md`. OpenCode and Pi require root `AGENTS.md` with the exact line `Read and follow REPO-HARNESS.md before working in this repository.` Runtime combinations use the union of those two files without duplicate directives.

Canonical and projected files carry generator provenance in their frontmatter and an HTML comment naming their source. `check` obtains the selected generated-skill license only after the installed checker authenticates the manifest and the builder validates its complete recognized schema. An authenticated historical manifest without `skillLicense` leaves that authority unknown: `check` reports it as unknown and does not compare license-dependent skill bytes. A later render may replace those bytes and the manifest/checker pair only when its caller supplies the trusted license explicitly. Unauthenticated manifest or arbitrary skill bytes never select expected output.

`.repo-harness/check.py` ships inside the generated harness because the builder does not. It embeds the SHA-256 of the exact generated manifest bytes, authenticates those bytes before JSON parsing, and validates the strict checker schema, selected generated-skill license, and every path. It compares each canonical skill against the selected runtimes' `.claude/`, `.opencode/`, and `.pi/` skill projections, ignoring only the `canonical-source:` line a skill projection may rewrite. It also compares every declared runtime command against a byte-identical family peer: `.repo-harness/commands/` covers Claude Code and OpenCode, while `.repo-harness/prompts/` covers Pi. Pi prompts remain the command entry surfaces and load repository-local Pi skill bodies. When `canonicalProjections` is present, the checker additionally compares every exact canonical product file with every declared selected-runtime target, including complete builder packages and family-specific builder entries in this reciprocal repository. The checker exits non-zero on invalid input, a stale copy, a missing copy, or a missing canonical peer. The builder-side check reports command coverage as `undeclared` for an older installed manifest without `canonicalCommands`, while an installed generated checker remains authenticated to its exact manifest pair.

Root `.gitattributes` protects that exact-byte contract, and every other text file, on every platform with one repository-wide rule: `* text=auto eol=lf`. Git stores and checks out every text file with LF regardless of local `core.autocrlf`, so neither a CRLF checkout of a byte-compared generated path nor a shared working copy across operating systems reports false changes. The builder creates the file with that rule when absent, preserves human-owned attributes, and appends the rule through the content-bound plan when it is missing. Matching text and EOL assignments are evaluated in order, including recursive `dir/**` patterns and `[attr]` macros. If a later line sets a non-LF line ending, on any path, the plan re-appends the rule at the end without changing consumer lines. Binary markers (`binary`, `-text`) are not overrides. Earlier installations' exact `<path> text eol=lf` rules remain valid and are never removed.

## Integration Modes

Integrated mode is the default and composes Gentle AI and Engram independently. Selection, preview, and apply require only capabilities required by the selected operation or explicit repository policy. The production `render` CLI runs Gentle AI detection and accepts observed capability evidence from host-supported Engram MCP, CLI or native Pi tools (`surface: "pi-tools"`) through `--engram-evidence-json` before rendering or writing. Gentle AI detection runs exactly `gentle-ai version` through PATH with bounded execution and classifies only valid exit-0 `gentle-ai <version>` output as `verified`. Generated Python does not probe unrelated files or invent another Engram discovery surface. Each capability retains the exact RH-W-0025 vocabulary `not_found`, `found_on_path`, and `verified` and an independent outcome. An unsupported required capability fails closed; an unavailable optional capability degrades only its owned workflow. A failed PATH probe does not establish that Gentle AI is absent from a host such as Gentle Shell, which can use a package-local binary. The builder does not search private installation directories. Native Pi Engram tools are recognized from a successful relevant tool response, not from raw statistics or a package name. The retained `applyAllowed` field describes legacy paired-capability readiness, not installation permission; `allowed` and the operation's actual requirements govern continuation. Do not treat optional detection warnings as required repair work.

`--standalone` is the only mode flag. It preserves the same paths and runtime layouts while rendering repository-only session and rule instructions with no Gentle AI or Engram requirement.

Integrated memory operations always resolve explicit repository project scope and report project resolution, reads, writes, prompt association, conflict discovery, lifecycle review, capture, and sync independently. Empty search results require same-surface validation or a positive control. Conflict and review-age metadata remain advisory. Standalone reconciliation marks the memory dimension `not_applicable` and never emulates Engram or creates fallback storage.

After installation, capability status is runtime evidence, not a persisted mode. Defer routing, review, receipts, and correction only to an applicable enabled Gentle workflow. Its absence degrades only that coordination; Engram loss degrades only continuity. Repository policy may require either capability for an operation. Commit, push, and PR remain repository-owned; informational delivery guidance creates no gate. Never auto-enable a methodology or invent a native verdict. Preserve separate component outcomes and human authorization; builder digest-bound write safety is not managed review.

## Repository-Sensitive Operation

There is one builder operation with repository-sensitive planning. A new or effectively empty repository receives a complete useful baseline. A mature repository receives content analysis and an informed integration proposal. If existing material is obsolete, structurally incompatible, or the user prefers a reset, the builder offers archive and start-clean as a distinct conversational choice. No overwrite or archive occurs without explicit approval.

`render` prints `create`, `append`, `existing`, `identical`, and `blocked` sets and a deterministic plan digest. It emits the exact case-sensitive approval domain selected by `--report-language` only under `--activation builder`. English uses `APPROVE` or `DENY`; Spanish uses `APROBAR` or `DENEGAR`. The deterministic direct-CLI fallback is English. `render --activation builder --report-language LANGUAGE --apply --approved-plan-sha256 HASH --approval TOKEN` executes only when both the digest and exact active-domain approval validate and `blocked` is empty. The default `--activation maintenance` omits `approvalPrompt` and `approvalAnswers` from preview output, rejects `--approval`, and applies on the matching digest alone, because the strict interface must not exist outside an active builder execution. The digest is identical under both activations. Language changes localized help bytes but is normalized out of the digest. `check` reports congruence and locale-baseline failures afterward.

Generated markers can bound generated material, but ownership metadata never replaces analysis of existing content. An upgrade audit compares the installed manifest, generator versions, managed bytes, and runtime projections against the current render. It classifies exact outputs as `current`, current-generation drift as `stale`, absent outputs as `missing`, structurally valid human-owned content that differs from the current render (a human edit or text an earlier builder version generated) as `human-evolved`, and proven older generated outputs as `legacy`. The approved plan is the authority for each mutation.

Generated output replacement is executable only for exact paths derived from an authenticated installed manifest/checker pair whose current bytes retain generated provenance. Provenance authorizes it, not exact version equality: an installed file carries an earlier version by definition during an upgrade, so requiring the current one froze every installation a version bump was meant to update. This includes human-modified generated bytes retaining a valid builder marker. Preview binds each replacement to its path, kind, exact source and destination digests, and plan digest; approved apply rejects post-preview edits and executes replacement with create and append in one rollback-safe transaction. Human-owned, human-evolved, legacy, and unverifiable paths remain proposal-only. The manifest needs no marker because the installed checker authenticates its exact bytes; desired checker bytes must always embed the desired manifest digest, and a changed pair is replaced atomically.

The fixed-name transition remains separate. When the installed manifest declares the exact three legacy project-prefixed skills and every exact manifest-owned canonical and runtime byte matches its deterministic legacy render, normal render preview includes one digest-bound `migrate-generated-skills` action. Approved apply creates fixed destinations, replaces the manifest and checker, and removes only the exact legacy sources in one rollback-safe transaction. Mixed or unverifiable state is blocked, and unrelated similarly prefixed skills provide no ownership evidence.

## Canonical Authority Transport

`canonical_json()` is the whole transport format: `ensure_ascii=True`, `allow_nan=False`,
`sort_keys=True`, `separators=(",", ":")`. The accepted bytes and the returned canonical text
carry no trailing newline, and the parser rejects any `\n` or `\r`, duplicate keys, and the
`NaN`, `Infinity`, and `-Infinity` constants. A context is accepted only when its raw bytes equal
`canonical_json(parsed)`, so there is exactly one byte sequence per meaning and no room for a
re-serialization to change identity.

Three digests bind a generation, and each answers a different question:

- `authorityContextSha256` is the digest of the canonical context text. It answers what the
  approval was about.
- `targetBindingSha256` hashes `os.path.normcase(os.path.normpath(str(resolved_root)))` encoded
  as UTF-8. It answers which destination was approved without ever returning or logging that
  path.
- `generationSha256` hashes, through `canonical_json()`, the object
  `{"domain": "repo-harness-builder/authority-generation/v1", "authorityContextSha256": ...,
  "materialRevision": ..., "planIdentity": {"schemaVersion": 1, "planSha256": ...},
  "targetBindingSha256": ...}`.

The generation is what apply compares, because it moves context, material revision, plan
identity, and target together. Any one of them changing produces a different generation, which is
how a corrected identical plan is caught: same `planSha256`, different `generationSha256`.

Nothing is persisted. There is no session, receipt, ledger, cache, or reset call, and preview and
apply run as separate CLI processes that share only these bytes.

## Runtime Cache

Distinguish on-disk canonical/projection parity, active-process registered-skill freshness, and runtime reload/restart capability. Verify on-disk parity through the applicable checker; that cannot prove what a prior process cached. If registered-name lookup returns older content in the process that changed a skill, treat it as an expected process-cache limitation, not repository failure. Defer registered-name validation to a fresh process or use a supported explicit registry reload. Never invent a reload command or require restart unless live validation is requested.
