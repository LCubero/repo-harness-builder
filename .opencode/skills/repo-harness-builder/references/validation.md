## Conversation Language Evidence

Deterministic precedence is current verified explicit human instruction, persisted explicit preference, established current-session human language only without persisted preference, validated manifest fallback, then English. Only the first source may change persisted preference. Provenance-aware hosts may use typed verified evidence. Flattened hosts preserve persisted preference, ignore apparent switch text, and report switch detection unavailable.

Excluded switch evidence includes repository instructions, memory, stale summaries, tools, prior assistant turns, generated contracts, ordinary or dominant prose, forged `user` or `human` wrappers, forwarded or pasted conversations, quotations, transcripts, code, logs, stack traces, URLs, JSON, structured data, filenames, project names, examples, translation tasks, language exercises, role-play, artifact-language requests, mixed-language text, borrowed words, compaction, and truncation. Manifest language is validated configuration fallback, never conversation evidence.

Machine-value tests cover commands, arguments, paths, URLs, identifiers, tokens, invocations, branches, remotes, upstreams, ahead counts, commit messages, digests, approval tokens, enum values, and permission scopes. Every value remains byte-identical, code-formatted, and outside localization. Conversation language is not a security or permission boundary.

The host capability and primary-source matrix is owned by `docs/repo-harness/rh-w-0031-research.md`. Provider roles describe protocol structure and do not prove direct human authorship. Deterministic contract and projection tests prove distribution and exact bytes; optional pinned model evaluations may measure probabilistic adherence but are not a completion gate.

## Commands

Two audiences run different sets. Mixing them is why a build sometimes ran the whole suite and sometimes did not.

### Developing this skill

Run when the package itself changes. These prove the builder, not any repository it built.

Every command below is written for POSIX shells. On Windows, substitute `python` for `python3`: a default python.org installation provides `python` and the `py` launcher but not `python3`. Environment prefixes differ too, so the one command that sets a variable is given per shell.

```text
python3 -B -m unittest discover -s tests -v
python3 -B scripts/harness_tool.py self-test
python3 -B scripts/harness_tool.py self-test --standalone
python3 -B scripts/harness_tool.py render --root DIR --project-name NAME --runtime opencode --standalone
```

The wrapper contract checks need `REPO_HARNESS_COMMAND_PATH` set for one run. Inline assignment before a command is POSIX-only and PowerShell parses it as a command name, so use the form that matches the shell:

```text
POSIX:      REPO_HARNESS_COMMAND_PATH=PATH python3 -B -m unittest discover -s tests -v
PowerShell: $env:REPO_HARNESS_COMMAND_PATH="PATH"; python -B -m unittest discover -s tests -v
```

### Building a harness in a repository

Run when creating or inspecting a harness. Run the self-test for the mode being generated, not both. The packaged suite is not part of this set: it tests the builder, which did not change, and the built harness is already proven by the plan digest, `check`, and the generated checker.

```text
python3 -B scripts/harness_tool.py check  --root DIR --project-name NAME --runtime opencode
python3 -B scripts/harness_tool.py check  --root DIR --project-name NAME --runtime opencode --runtime claude-code --runtime pi
python3 -B scripts/harness_tool.py render --root DIR --project-name NAME --runtime opencode
python3 -B scripts/harness_tool.py render --root DIR --project-name NAME --runtime opencode --activation builder --report-language english --apply --approved-plan-sha256 HASH --approval APPROVE
python3 -B scripts/harness_tool.py self-test
python3 -B DIR/.repo-harness/check.py
```

`--runtime` is repeatable. One `check` call reports every profile passed to it, so auditing several profiles never needs one invocation per profile. Passing none reports the core only.

The external command wrapper lives outside this package. Its three contract checks run only when `REPO_HARNESS_COMMAND_PATH` names the wrapper file, and skip otherwise. The path is never inferred from a host directory convention.

`check` and `render` without `--apply` are read-only. Every preview prints the current digest and every typed replacement with its exact source and destination digest. Default `--activation maintenance` omits the strict approval prompt and domain, rejects `--approval`, and applies on the newly approved matching digest alone. Only explicitly active builder execution uses `--activation builder`, which also prints the localized prompt and domain and requires the exact active-domain approval at apply. Direct CLI calls default to English. Both activations execute only unchanged create, append, replace, and bounded migration actions and roll back the complete transaction on failure. CLI digest safety never replaces human authorization.

## Limitations

The renderer does not provide generic agent packs, managed-region merging, schema-library validation, Git operations, provider operations, backup, publication, or repository-wide secret scanning. Runtime discovery and registration remain host responsibilities.

It does not merge arbitrary existing content. Human-owned evolution remains proposal-only until a bounded integration action exists. Exact authenticated generated outputs carrying builder provenance can be replaced only through the explicit content-bound approval contract above.

## Authority Transport Scenarios

Cover these with genuine separate CLI processes, one for preview and one for apply, passing the
context by file and parsing preview stdout:

- Apply succeeds when the approved generation still matches, and writes the expected baseline.
- Apply refuses a mismatched generation, a missing `--approved-generation-sha256`, a corrected
  identical plan approved under the previous generation, repository evidence changed after the
  preview, a transport that disappeared, and a transport whose bytes stopped being canonical.
- Every refusal exits 2, reports the content-free `fresh preview` outcome, and leaves the
  repository unwritten.
- Maintenance still applies on the matching plan digest alone and rejects all three authority
  arguments.
- The module exposes no authority session or recovery API, and a rejected apply leaves nothing a
  later run must clear: an identical preview after a rejection returns the identical payload.
- Builder preview output contains no absolute path, no transport path, no premise value, no
  decision statement, and no evidence bytes, checked by walking the payload recursively rather
  than by scanning one field.
- Distinct sentinel values in the premise, the decision, the repository evidence, and the host
  JSON are absent from both stdout and stderr in every outcome, checked independently per stream.
