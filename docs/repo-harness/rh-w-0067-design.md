## Decision

One generated `.repo-harness/rules/response-contract.md` owns the complete response-shaping contract. `REPO-HARNESS.md` carries one routing row. Each daily Output Contract retains one obligation sentence and points to the rule owner. No other generated surface repeats the syntax.

RH-W-0067 also owns one concise semantic clause: when context is relevant, explain the dimensions needed to understand or act, chosen from why, purpose, location, timing, and method. It does not require five headings, five sentences, or all five dimensions.

## Rendered Content Contract

The generated rule file contains these sections and obligations:

1. Builder provenance using `<!-- Generated by repo-harness-builder; source: core/rules:3.0 -->` through the existing marker and version constants.
2. `Load when:` routing for any answer requiring a notice, pending action, question, approval, visible next action, or contextual explanation.
3. `## Visibility`, owning the complete RH-W-0058 obligation.
4. `## Contextual Explanation`, owning the new bounded semantic clause.
5. `## Preserved Boundaries`, linking rather than copying proportionality, evidence classification, authority, no-unrequested-work, and authorized-follow-through rules.
6. `## Budget`, using the same existing development-time rule-file budget wording and constant as the sibling rule files.

The visibility section requires:

- A notice, pending action, or question that must survive skimming gets a separate block with a short label in the reply language.
- A blocked reply that cannot continue until the human answers uses exactly 32 `=` bytes above and below the label, explanation, and single final question.
- A reply that asks nothing and names a visible next action uses exactly 32 `+` bytes above and below the label and next action.
- One reply never contains both block forms.
- `=` is never used for informational content, and `+` never asks a question.
- Side borders and box corners remain forbidden.
- When nothing is pending and no visible next action is useful, close with a plain status line and one concrete recommendation, never an empty block.
- The contract binds the agent's own replies and reported output and strengthens, rather than replaces, the existing single-final-question rule.

The literal blocked form is:

```text
================================
Decision required

<Only the context needed to answer.>

<One concrete final question?>
================================
```

The literal non-blocking next-action form is:

```text
++++++++++++++++++++++++++++++++
Next action

<One concrete next action.>
++++++++++++++++++++++++++++++++
```

Each delimiter line contains exactly 32 copies of its character and no spaces. The opening and closing lines are byte-identical.

### Markdown Setext Warning

A line of `=` directly below ordinary prose can be parsed as a setext heading and disappear as a delimiter. Therefore the blocked form always starts after a blank line, contains its label and body between two standalone 32-byte lines, and never places its opening delimiter directly under prose without that blank line. The fenced examples are literal output examples, not Markdown to copy without preserving their blank-line boundaries.

### Contextual Explanation Semantics

When an answer needs context for the human to understand or act, explain only the relevant dimensions among:

- why the matter exists or the decision follows;
- its purpose;
- where it applies;
- when it applies or must happen;
- how to act or verify.

The clause is semantic and proportional. It explicitly rejects five mandatory headings, a fixed template, empty dimensions, repeated information, and explanations where the answer is already self-explanatory. Existing evidence classes govern every factual claim; this clause does not replace or restate them.

```text

```

The three daily contracts retain the obligation. They no longer own or duplicate delimiter characters, counts, examples, setext behavior, contextual dimensions, or fallback syntax. `VISIBILITY_CONTRACT` may be renamed to reflect the retained reference or inlined once per renderer only if the implementation keeps one shared source string and the rendered sentence above remains exact.

## Delimiter Decision

The exact length is 32 ASCII bytes for both forms.

Measured repository evidence establishes that three characters failed twice to provide the intended visual distinction. The local terminal used for repository verification is 120 columns. The design does not consume that width: 32 is only 27 percent of it and still fits with eight columns of margin on a deliberately narrow 40-column surface. A shorter 20 or 24 character line gives less separation from ordinary prose; 40 or more assumes the entire narrow surface. Thirty-two is also directly countable as four groups of eight in tests and byte review. No Unicode rule characters are allowed.

## Migration And Upgrade Behavior

- A fresh render seeds the new response rule and the gate row.
- An existing installation without the file reports it as missing and receives the normal generated-output create action only through an authorized render or apply.
- Existing daily skills and runtime skill projections become stale and follow current authenticated replacement behavior.
- A human-evolved response rule is preserved and structurally checked under the existing rule-file policy; this unit adds no automatic rewrite or special migration.
- The manifest format, checker format, generator version, write semantics, approval model, and package-freshness classification do not change.
- RH-W-0013 implementation must land first so a budget crossing cannot block render or become checker drift. Development-time template tests still reject an oversized generated template.

## Rollback

Rollback is one work unit: remove the response rule from `rule_outputs()`, restore the prior rulebook template, restore the prior shared daily contract text, regenerate canonical and runtime projections, and rerun the same checks. No data migration, manifest rollback, schema downgrade, or state cleanup is required. Human edits to an installed response rule remain human-owned and are never deleted automatically.
