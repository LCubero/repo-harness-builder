# Decisiones y restricciones

La fuente canonica es [`../../repo-harness/decisions.md`](../../repo-harness/decisions.md).

## Decisiones permanentes
<!-- doc-role:standing-decisions -->

- Las salidas generadas existentes de la version actual solo pueden reemplazarse cuando el par autenticado de manifest y checker instalado prueba la ruta exacta de su propiedad y los bytes actuales conservan procedencia generada. Esto incluye modificaciones humanas que retienen un marcador valido de la version actual. El preview liga ruta, tipo de accion, SHA-256 exacto de origen y destino y digest del plan; apply rechaza ediciones posteriores al preview y revierte cada create, append y replace ante cualquier fallo. Las rutas de propiedad humana, evolucionadas por humanos, heredadas o no verificables permanecen solo como propuesta. El checker deseado debe coincidir con el digest del manifest deseado y un par valido cambiado se reemplaza atomicamente.
- `repo-harness` es un sistema acotado al repositorio de prompts, guardrails, reglas del harness, documentacion durable, habilidades y comandos que fortalece y asiste a agentes de programacion con IA como OpenCode, Claude Code y Pi. `repo-harness-builder` crea, audita, instala y evoluciona con seguridad ese sistema dentro de un repositorio seleccionado. El harness es util de forma independiente en modo standalone y puede usar componentes opcionales del ecosistema segun el modo de integracion seleccionado. Gentle AI es el ecosistema mas amplio de enrutamiento, revision, recibos y entrega; Engram aporta continuidad semantica sin reemplazar la verdad del repositorio; y CodeGraph es la ayuda mas opcional de inteligencia y navegacion de codigo local al repositorio, nunca un almacen de autoridad. Hermes Agent, OpenClaw y Pi son solo fuentes de inspiracion, no dependencias ni productos que este proyecto recrea.
- Un harness instalado debe poder actualizarse en un solo pase. Una subida de version del constructor no puede congelar las instalaciones que existe para actualizar, de modo que la autoridad de reemplazo sigue la procedencia del constructor y no la igualdad exacta de version, y una reparacion en dos pases no es una ruta de actualizacion aceptable. Una ruta sin procedencia del constructor sigue siendo de propiedad humana y solo propuesta en cualquier caso. Ningun repositorio consumidor se modifica jamas para desbloquear al constructor, y este repositorio no planifica trabajo dentro de uno: instalar y ejecutar un release es una accion del propietario y no una tarea que este repositorio agende.
- La evidencia actual del repositorio prevalece sobre memoria previa.
- Una afirmacion es un hecho verificado solo cuando la respalda evidencia aplicable, confiable y proporcional. Las inferencias respaldadas declaran su evidencia y razonamiento; las afirmaciones sin un mecanismo valido permanecen desconocidas o no verificables; y las decisiones humanas se solicitan solo cuando la autoridad o el criterio corresponden a una persona. La ausencia de evidencia, memoria obsoleta, indicadores indirectos no relacionados, supuestos y lenguaje de confianza nunca sustituyen la verificacion. Se usa la verificacion disponible antes de preguntar; cuando no esta disponible o es contradictoria, el flujo nombra la capacidad faltante y solicita solo la evidencia, el criterio, la autoridad o la decision minima.
- Git, GitHub, issues, pull requests, `CONTRIBUTING.md`, Gentle AI, Engram, CodeGraph, tooling de proveedor e integraciones similares son opcionales. Su ausencia o fallo degrada solo la capacidad que cada integracion posee y nunca permite prometer garantias respaldadas por Git cuando Git no esta disponible. Git es altamente recomendado porque mejora historial, diferencias, recuperacion, rollback, ramas, commits y seguridad de entrega. Sin Git, se da una sola advertencia o recomendacion util de que Git es el minimo preferido para seguridad completa, y luego continua la operacion sin Git soportada, sin rechazo ni preguntas repetidas.
- `skill/repo-harness-builder/` y `command/repo-harness-builder.md` son fuentes editables; `.claude/`, `.opencode/` y `.pi/` son proyecciones de los entornos seleccionados.
- Cada entorno seleccionado lleva copias locales al repositorio de las habilidades operativas que invocan sus superficies de entrada. Claude Code y OpenCode conservan comandos, Pi conserva prompts y los tres usan los mismos cuerpos canonicos con solo la normalizacion existente de procedencia `canonical-source:`. La sintaxis propia de cada familia nunca justifica depender de un registro global de habilidades.
- Este repositorio desarrolla reciprocamente `repo-harness-builder` y ejecuta su `repo-harness` generado contra la misma fuente de producto como campo de prueba autoalojado. La paridad completa aqui incluye para cada entorno seleccionado la proyeccion exacta del paquete del builder, su entrada invocable propia de la familia, las tres habilidades operativas generadas y sus entradas. El campo autenticado opcional `canonicalProjections` del manifest registra proyecciones exactas del producto solo cuando existen fuentes canonicas del builder; los manifests de consumidores ordinarios lo omiten. La politica especifica del repositorio autoalojado es evidencia, no comportamiento generico del producto por defecto.
- Antes del release, cada comportamiento relevante se clasifica como scaffolding exclusivo del builder, politica especifica del repositorio o contrato generico del consumidor. El release exige que el contrato generico produzca un harness operativo, correcto, funcional, recuperable y capaz de mejorarse para cualquier tipo de proyecto, sistema operativo y agente compatible. La disciplina de evidencia anterior gobierna esta clasificacion; esta decision no la duplica.
- Si Git existe pero la carpeta seleccionada no esta inicializada, solo se ofrece inicializarla despues de aprobacion humana explicita. La publicacion mediante proveedor sigue siendo un limite opcional con aprobacion separada y eleccion explicita de visibilidad.
- Los repositorios nuevos reciben una base completa; los existentes reciben analisis e integracion propuesta, nunca sobrescritura automatica.
- Los marcadores generados delimitan material, pero no eximen documentos humanos del analisis.
- Solo una ejecucion explicitamente activa de la habilidad `repo-harness-builder` usa tokens estrictos localizados y ligados al digest para su plan de aplicacion ligado al contenido: en ingles, `APPROVE` o `DENY`; en espanol, `APROBAR` o `DENEGAR`. La aplicacion exige tanto el digest como el token exacto. Las llamadas directas a la CLI usan ingles de forma predeterminada y el idioma nunca forma parte del digest del plan. La identidad del repositorio, el autoalojamiento, el mantenimiento ordinario del repositorio, la propiedad de archivos generados, las habilidades de sesion y las preguntas directas no activan esta interfaz. Fuera de una ejecucion activa de la habilidad del constructor, la aprobacion sigue siendo conversacional.
- Ese limite lo impone la CLI, no solo la prosa. `render` acepta `--activation builder|maintenance` y su valor predeterminado es `maintenance`, que omite por completo `approvalPrompt` y `approvalAnswers` de su salida, rechaza `--approval` y aplica unicamente con el digest coincidente. La razon es que un preview que siempre imprimia el sobre estricto entregaba a cualquier invocador una interfaz de aprobacion lista para retransmitir, de modo que el contrato decia una cosa y la herramienta hacia otra. Una interfaz que no debe existir fuera de una ejecucion tampoco debe emitirse fuera de ella. El digest del plan es identico bajo ambas activaciones.
- Los punteros raiz preservan bytes y agregan solo una directiva exacta faltante.
- Los harness anteriores se clasifican antes de proponer reemplazo, archivo o eliminacion.
- Las aprobaciones de cierre son puntos reanudables y las acciones aprobadas se ejecutan una vez. El [diseño implementado de RH-W-0068](rh-w-0068-documentation-closure-design.md#closure-outcomes) conserva el trabajo verificado, pero impide completar cuando la documentación obligatoria se declina, queda pendiente, falla o está incompleta. El [diseño RH-W-0074](rh-w-0074-design.md), implementado el 2026-10-01, separa terminar una conversación de cumplir obligaciones sin un estado global nuevo de éxito: una declinación aceptada se informa como `declined` con la unidad de trabajo sin completar, y `paused` o `blocked` se usan solo para información realmente pendiente o requisitos realmente faltantes. Un fallo de continuidad opcional se informa por separado y no impide el informe del repositorio.
- El inicio sincroniza solo despues de inspeccion y aprobacion; nunca usa pull ciego, rebase, reset o resolucion automatica.
- El cierre completa documentacion y continuidad antes de Git. El consentimiento combinado cubre alcance exacto, commit, comprobaciones, un fetch y un push mientras los hechos no cambien.
- Los resultados `ready`, `paused`, `blocked`, `failed`, `completed` y `degraded` tienen alcance separado para continuidad y Git opcional.
- Cada aprobacion pendiente aparece como una unica pregunta concreta; las propuestas de commit incluyen rutas, justificacion, mensaje, exclusiones y estado preparado.
- La verificacion autoalojada separa paridad en disco, vigencia registrada del proceso y capacidad de recarga.
- `REPO-HARNESS.md`, `CHANGELOG.md` y los documentos durables en ingles conservan la propiedad factual unica. Los pares en espanol son presentaciones completas.
- La validacion bilingue combina roles semanticos y bases proporcionales de contenido por idioma, sin afirmar que una maquina prueba equivalencia semantica.
- Los idiomas de documentacion declarados y el idioma de conversacion controlan la ruta de ayuda generada, por lo que solo puede nombrar una guia que la misma generacion crea. El idioma del informe es presentacional y no cambia ningun byte generado, asi que el digest del plan es identico entre idiomas sin normalizacion.
- Los selectores README son atomicos: sin integracion reciproca ejecutable, `README.es.md` queda bloqueado y toda aplicacion falla de forma segura.
- Las contribuciones usan issue primero, ramas cortas, PR enlazado, Conventional Commits y pruebas con documentación en la misma unidad; requieren revisión del maintainer antes del merge. Con el acuerdo del propietario y una entrada en el changelog, las correcciones pequeñas de documentación, erratas y actualizaciones de conteos pueden ir directamente a `main`; un maintainer también puede autorizar explícitamente una excepción de emergencia. La aprobación es conversacional porque no existen labels, templates ni checks personalizados para imponerla.
- `docs/repo-harness/roadmap.md` es el propietario canonico del ciclo de vida no trivial. Los registros inmutables `RH-W-####` usan prioridad justificada y estado controlado; `current-state.md` solo proyecta actividad, los pares localizados reflejan al propietario y el tema de Engram `work/RH-W-####` refleja resultados sin poseer el backlog.
- La documentacion humana del repositorio admite declaraciones solo en ingles, solo en espanol o bilingues. La salida monolingue usa rutas canonicas; la bilingue conserva propietarios canonicos en ingles y agrega pares completos en espanol. Las habilidades, contratos, wrappers, verificadores, instrucciones y esquema del manifest, codigo, comentarios, instrucciones de runtime y artefactos tecnicos permanecen en ingles.
- Las decisiones bloqueantes de idioma son transiciones reanudables: despues de cada respuesta, el constructor emite de inmediato la siguiente pregunta requerida en el turno siguiente y vuelve a detenerse. Nunca espera texto de relleno ni combina dos preguntas bloqueantes.
- Lo que el agente lee y lo que le dice a la persona usuaria son elecciones separadas. Los locales de documentacion gobiernan las superficies de lectura disponibles y su valor predeterminado es solo ingles; el locale de la guia nunca determina el idioma de respuesta. El idioma de conversacion sigue una instruccion humana explicita actual verificada, luego una preferencia explicita persistida, el idioma verificado de la sesion solo cuando no existe preferencia persistida, el fallback validado del manifest y finalmente ingles determinista. Solo una instruccion humana explicita posterior verificada cambia la preferencia persistida. La prosa ordinaria y los bytes contextuales no son evidencia de cambio, y la resolucion del idioma nunca modifica bytes significativos para la maquina ni el alcance de permisos.
- Los comandos autoalojados de render propietario, preview y apply siempre pasan de forma explicita el conjunto instalado de runtimes, la licencia, el idioma del informe, los locales de documentacion y el idioma de conversacion. El manifest autenticado conserva la licencia seleccionada de las skills generadas porque es el estado confiable minimo desde el cual `check()` canonico puede reproducir los bytes esperados de instalaciones no MIT; los bytes arbitrarios de skills instaladas nunca la suministran. Los manifests historicos autenticados sin ese campo conservan autoridad de licencia desconocida y no pueden seleccionar ni reemplazar bytes dependientes de licencia hasta que el propietario suministre explicitamente la licencia confiable; esa actualizacion autorizada mantiene atomico el par manifest/checker. La paridad del checker generado prueba consistencia con el manifest instalado; no sustituye una comprobacion explicita de idempotencia del render propietario.
- Cada repositorio generado protege cada ruta generada comparada byte a byte con una regla exacta `<path> text eol=lf` en `.gitattributes` raiz: checker, manifiesto, habilidades y familias de comandos canonicos, proyecciones de runtime, wrappers y proyecciones exactas opcionales del producto. Punteros, archivos de ignorado, atributos y documentos humanos quedan fuera de este contrato de rutas generadas. Los atributos humanos existentes conservan sus bytes, las reglas exactas faltantes se agregan mediante el plan aprobado ligado al contenido y las reglas coincidentes incompatibles bloquean antes de escribir. Este contrato del constructor es distinto de la politica LF mas amplia de este repositorio fuente en `CONTRIBUTING.md`.
- La coordinacion consciente de capacidades conserva los limites de cada propietario. El repositorio posee verdad durable, fuente y pruebas, politica, backlog y aprobaciones. Gentle AI y Engram son capacidades opcionales independientes que se componen de forma independiente, sin modo emparejado, tercer estado ni autoridad copiada. Se delegan enrutamiento, revision del candidato exacto, recibos y correccion solo al flujo Gentle aplicable y habilitado, sin revisores, contadores, recibos ni planes paralelos. No se activan RDD/SDD ni revisiones deshabilitadas automaticamente. La politica del repositorio posee commit, push y PR; la orientacion informativa de entrega no agrega compuertas. La seguridad de escritura vinculada al digest del builder es distinta de la revision administrada; ninguna sustituye la autorizacion humana. Engram posee continuidad semantica. RH-W-0025 completada conserva las clasificaciones `not_found`, `found_on_path` y `verified`; `available`, `unavailable`, `partial`, `disabled` y el `policy-required` contextual siguen como estados efectivos, no clasificaciones. La ausencia o fallo causa degradacion acotada a la operacion, salvo que la politica exija esa capacidad para la operacion.
- **Hecho verificado (actualización actual, 2026-09-17):** los snapshots locales seleccionados son `gentle-shell` [`2b579c80824e83442b8ae9f7bfad629a52f9f711`](https://github.com/Gentleman-Programming/gentle-pi/tree/2b579c80824e83442b8ae9f7bfad629a52f9f711), Gentle AI [`eae8fadd5ece2622cb072c836fa49cef520afc8e`](https://github.com/Gentleman-Programming/gentle-ai/tree/eae8fadd5ece2622cb072c836fa49cef520afc8e) y Engram [`f6b22f89d024fb6aaa207606d893f47b3f4e23a9`](https://github.com/Gentleman-Programming/engram/tree/f6b22f89d024fb6aaa207606d893f47b3f4e23a9). Son evidencia de actualización, separada de los pines históricos. `gentle-shell` es el nombre actual del producto/repositorio orientado a Pi, mientras que `gentle-pi` permanece en identidades de npm, runtime, paquete y repositorio fuente; es una transición de nombres mixta en curso, no un cambio de nombre de paquete ya completado. **Restricción permanente:** `gentle-shell` puede poseer la orquestación nativa de Pi, subagentes acotados, artefactos de tareas ODD y su espejo de Engram con alcance de proyecto, SDD opcional, contratos de transporte/espejo de revisión y composición opcional con Engram. Cada tarea ODD sustancial cierra con un commit de unidad de trabajo; los candidatos de revisión nativa son commits de unidad de trabajo o cortes de PR, nunca una casilla ni una rama de funcionalidad acumulada; y la planificación de entrega encadenada aplica alrededor de 400 líneas modificadas de autoría. Cuando la política de subagentes en segundo plano está activa y `subagent_run` está disponible, la delegación ordinaria se ejecuta en segundo plano de forma predeterminada. El espejo de Engram es específico de la coordinación ODD, no de toda la capacidad de Engram; `gentle-shell` no posee la semántica de revisión nativa. Gentle AI mantiene ODD como predeterminado, SDD seleccionado explícitamente y RDD como propiedad de la persona usuaria y opcional; archivar SDD no es aprobación de revisión ni entrega. El formato de backup directo `0.2.0` de Engram conserva pines locales y metadatos completos de relaciones de memoria, mientras acepta backups heredados `0.1.0` que los omiten.
- Las operaciones de Engram del harness exigen alcance explicito de proyecto. Engram aporta continuidad semantica, no autoridad sobre backlog, aprobacion, entrega, clasificacion, reconciliacion, estado del repositorio, fuente, pruebas ni decisiones humanas.
- Los resultados de Engram son evidencia por operacion, no un unico veredicto disponible, degradado o ausente. Se informan por separado resolucion de proyecto, lectura local, escritura local, asociacion de prompt, descubrimiento de conflictos, revision de ciclo de vida, captura del plugin y sync cuando apliquen. Guardar una observacion conserva su exito aunque falle la captura de prompt o el descubrimiento posterior de candidatos.
- Los candidatos de conflicto son consultivos. `judgment_required` significa que se produjeron relaciones candidatas y no prueba contradiccion. `active` y `needs_review` son etiquetas de antiguedad calculadas desde `review_after`, no estados de verdad, verificacion, autoridad, expiracion o borrado.
- La captura del plugin de OpenCode, la captura automatica de prompt, el handoff por compactacion y la captura pasiva son canales de mejor esfuerzo cuyo exito requiere evidencia. La implementacion local-first actual de Engram sobre SQLite es un detalle verificado, no una dependencia exigida por el harness; futuras implementaciones compatibles pueden conservar el contrato mediante otro limite local soportado.
- Los descubrimientos durables y reutilizables se promueven selectivamente al propietario canonico correcto solo despues de aprobacion humana. Los hechos externos cambiantes se marcan como actuales y se revalidan antes de reutilizarlos; el ruido incidental no se persiste. Los harnesses generados para consumidores nunca mencionan mejorar `repo-harness-builder`; este repositorio autoalojado aplica el mismo contrato generico a su propia fuente de producto. La coordinacion nunca habilita revision automaticamente, fabrica aprobacion, crea SDD sintetico, duplica almacenes de ciclo de vida, recibos o conflictos, ni repite hasta quedar limpia.
- La instalacion del builder detecta Gentle AI mediante ejecucion acotada por PATH, sin shell, de `gentle-ai version`, no mediante el layout de instalacion. Un fallo al crear el proceso es `not_found`; timeout, salida distinta de cero o formato invalido es `found_on_path`; solo salida 0 con texto normalizado `gentle-ai <version>` es `verified`. La evidencia de instalacion de Engram procede del limite MCP o CLI soportado por el entorno. Seleccionar, aprobar y aplicar el modo integrado exige solo las capacidades requeridas por la operacion y conserva resultados independientes. El inicio rutinario reutiliza la recuperacion de Engram como evidencia de disponibilidad y comprueba Gentle AI solo en su limite de coordinacion habilitado. Un fallo de memoria opcional es visible, pero no impide el informe del repositorio. Ejecutar un binario de PATH supone la misma confianza que ejecutar `git` o `python`.
- Las ramas mergeadas se borran, y `deleteBranchOnMerge` esta activado en el repositorio para que GitHub elimine la rama de origen automaticamente. Borrar una rama mergeada no pierde nada: los commits siguen alcanzables desde `main` y GitHub conserva de forma permanente la pull request con su nombre de rama, su diff, sus commits y su conversacion. Las ramas se conservan solo mientras no esten mergeadas, sean de larga vida o algo externo las referencie. El 2026-08-15 el ajuste estaba apagado y se habian acumulado 16 ramas obsoletas; se borraron tras verificar que cada una estaba mergeada, y `docs/record-optional-codegraph` se borro solo despues de confirmar que su registro `RH-W-0026` era identico byte a byte en `main`.
- Una regla que el agente debe seguir internamente no queda aplicada hasta que el contrato de salida exige que sea visible. `REPO-HARNESS.md` clasifica cada afirmacion como hecho verificado, inferencia sustentada, desconocido o no verificable, o decision humana requerida, y los Output Contract diarios exigen ahora que esa clase aparezca en el informe, que una inferencia nombre la evidencia en la que se apoya y que la elevaria a verificada, y que nunca se presente en forma asertiva. Es una obligacion reforzada y no una compuerta: `check.py` compara bytes y no puede aplicar una regla de prosa sobre salida en prosa, de modo que se defiende por revision y no por codigo de salida.
- La posicion no es visibilidad. `.repo-harness/rules/response-contract.md` es el unico propietario completo de la sintaxis de pregunta bloqueante y siguiente accion informativa, incluidas las formas de delimitador, etiquetas, seguridad setext y cuando no corresponde un bloque. Cada Output Contract diario lleva solo la referencia concisa que aplica ese propietario a la respuesta del agente y la salida informada. La regla sigue defendida por revision porque `check.py` compara bytes y no puede juzgar salida en prosa.
- Anunciar trabajo ejecutable no es darle seguimiento. Cuando una verificacion o accion es inmediatamente ejecutable dentro del alcance pedido y autorizado, el agente la ejecuta e informa el resultado en vez de detenerse despues del anuncio. Solo pausa por aprobacion, autoridad, evidencia, seguridad o una decision material. Esta regla general pertenece en `REPO-HARNESS.md`; no autoriza tareas no pedidas, no reutiliza aprobacion, no debilita ningun limite de autoridad y no reabre el alcance de visibilidad que posee `RH-W-0058`.
- El almacenamiento personal propiedad de la persona usuaria queda fuera del limite del harness. Los contratos generados y la documentacion canonica del producto no nombran sus rutas ni dependen de ellas. El estado local propiedad del harness pertenece bajo `.repo-harness/` de forma predeterminada.
- El diseno RH-W-0051 aprobado e implementado asigna estado descartable a `.repo-harness/tmp/`, archivos recuperables a `.repo-harness/archive/`, estado pequeno de consumidores declarados a `.repo-harness/state/` y backups locales de sesion a `.repo-harness/memory-bk/`. Todos son no autoritativos e ignorados por defecto. Archivo y backups nunca se eliminan automaticamente al inicio. La implementacion verificada declara y comprueba la taxonomia sin agregar comportamiento consumidor.
- El diseño RH-W-0053 aprobado por el propietario asigna un único checkpoint activo de operación interrumpida a `.repo-harness/state/checkpoints/active.md`. Es no autoritativo, ignorado y solo se escribe ante una solicitud humana actual y explícita. El descubrimiento de inicio no muta ni reanuda automáticamente; la expiración semántica no elimina automáticamente; y toda reanudación vuelve a verificar evidencia actual y exige autoridad nueva. Los resúmenes RH-W-0069 y Engram siguen como continuidad separada y nunca se convierten en checkpoints ejecutables. El 2026-09-07 el propietario aprobó sin cambios el plan de implementación bilingüe; la implementación requiere autorización separada.
- El contrato de recuperación RH-W-0048 aprobado por el propietario e implementado recupera solo proyecciones de runtime locales y ausentes desde un manifiesto instalado autenticado y archivos canónicos declarados disponibles. El check ordinario sin comando sigue en solo lectura e informa `writes: 0`; solo `python .repo-harness/check.py repair --apply --approved-plan-sha256 <digest>` puede crear proyecciones autenticadas `missing-local`. `repair` solo muestra preview de forma predeterminada; rutas rastreadas ausentes, obsoletas, dañadas, inseguras, desconocidas o evolucionadas por personas solo se informan y conservan todos sus bytes. La evidencia del índice Git identifica excepciones rastreadas sin modo nuevo de manifiesto; sin Git, las proyecciones son locales por defecto. Repair reutiliza creación exclusiva, verificación por digest y rollback, y queda separado de update del builder y de RH-W-0052. Las proyecciones solo locales no reciben reglas nuevas de `.gitattributes`. La mutación hostil concurrente del sistema de archivos es un residuo fuera del modelo cooperativo del repositorio; no se agrega lock, servicio, coordinador de transacciones ni otro mecanismo. La evidencia histórica de implementación es 536 pruebas y 9 omitidas, checker `current` con 63 proyecciones y `writes: 0`, paridad de paquetes canónico/Claude Code/OpenCode/Pi y verificación independiente sin hallazgos. La reconciliación reabierta del contrato de mutabilidad y la verificación independiente de RH-W-0048 están completadas y entregadas mediante el PR #174, como consta en el [registro del roadmap](roadmap.md#rh-w-0048).
- La documentacion es verdad durable canonica por dominio; la memoria es continuidad operativa. Engram y backups son evidencia no autoritativa que se comprueba entre fuentes, nunca stores duplicados de documentacion, ciclo, aprobacion, conflictos, recibos o entrega. La evidencia actual resuelve afirmaciones antes de confiar en memoria y una decision material no resuelta vuelve a la persona.
- Reconciliar hallazgos es responsabilidad del harness.
