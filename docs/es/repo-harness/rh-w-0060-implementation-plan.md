# Plan de implementación RH-W-0060

**Estado: plan aprobado por el propietario.** El 2026-09-30 el propietario aprobó este plan y delegó la implementación. El [diseño aprobado](rh-w-0060-design.md) posee el contrato; el [roadmap](roadmap.md#rh-w-0060) posee el ciclo de vida y la evidencia de verificación.

**Premisa verificada.** En un repositorio temporal con `core.autocrlf=true` y `eol=lf`, reescribir un archivo commiteado solo con CRLF hizo que `git status --porcelain` informara ` M`, mientras `git diff --quiet HEAD -- <ruta>` salió con 0. Un cambio sustantivo salió con 1, y un blob del índice diferente hizo salir con 1 a `git diff --cached --quiet HEAD -- <ruta>`. Git ya aplica el filtro de limpieza por ruta, así que la cláusula reutiliza esos dos comandos y no necesita herramienta nueva.

1. **RED.** Agregar una prueba enfocada junto a `test_session_stop_requires_classified_screened_commit_proposals` que renderice session-stop y exija como texto del contrato los cuatro resultados del diseño: una ruta rastreada cuyos `git diff --quiet HEAD -- <ruta>` y `git diff --cached --quiet HEAD -- <ruta>` salen ambos con 0 se informa como solo EOL/filtro, no modificada en contenido; salida 1 en la comparación del árbol de trabajo sigue modificada en contenido; salida 1 en la comparación del índice sigue modificada en contenido; cualquier otra salida, un blob `HEAD:<ruta>` ausente o un filtro ambiguo es `unknown` y nombra la evidencia faltante. Confirmar que falla antes del cambio.
2. **GREEN.** Agregar una oración después de la clasificación existente del paso 8 en la plantilla de session-stop de `skill/repo-harness-builder/scripts/harness_tool.py`. Solo se aplica a una ruta rastreada informada como modificada, nombra las representaciones comparadas y el resultado, y nunca oculta un cambio sustantivo. No cambia ninguna otra skill, resultado ni comando Git.
3. **Sincronizar y verificar.** Actualizar las salidas autoalojadas (`.repo-harness/`, `.claude/`, `.opencode/`, `.pi/`) con el preview de mantenimiento existente y apply con el digest actual. Ejecutar la prueba enfocada, luego la suite canónica, luego `python .repo-harness/check.py` (`current`, cero escrituras) y `git diff --check`.
4. **Entregar y cerrar.** Un issue y un PR. Tras el merge, registrar `completed` en roadmap y estado actual (EN/ES), mapas de documentación, `CHANGELOG.md`/`CHANGELOG.es.md` y el tema Engram `work/RH-W-0060`. El rollback es revertir el único commit.

**Límite declarado:** las pruebas demuestran el texto del contrato generado; no pueden demostrar que un agente lo siga. La prueba en el repositorio temporal es la evidencia de que los comandos Git nombrados se comportan como dice el contrato.

**No objetivos:** cambios en session-start, inventario de ramas (C12 está cerrado), limpieza automática, rediseño de `.gitattributes`, manejo de conflictos, cambios de transporte, comandos, estado o dependencias nuevos, e implementación sin autorización separada.
