# Fixed Repo Harness Skill Names Design

## Decision

Every repository generated by `repo-harness-builder` will use the same three generated skill names:

| Responsibility | Generated skill name | Command name |
|---|---|---|
| Start or resume a work session | `repo-harness-session-start` | `session-start` |
| Pause or close a work session | `repo-harness-session-stop` | `session-stop` |
| Maintain canonical documentation | `repo-harness-documentation` | `documentation` |

The generated skill names no longer depend on `project_id`. Command names remain unchanged through an explicit command-to-skill mapping. They are not derived by removing a project prefix.

This repository is the self-hosted integration fixture, but the behavior is a product rule for every repository rendered by the builder.

## Goals

- Give generated repo harness skills stable, recognizable names in every repository.
- Preserve the existing `session-start`, `session-stop`, and `documentation` command interface.
- Keep fresh installation additive.
- Allow normal render preview and apply to migrate a verifiable legacy installation safely.
- Reuse the bounded RH-W-0024 migration capability without widening it.
- Keep canonical source, runtime projections, manifests, commands, checks, and documentation consistent.

## Non-Goals

- A general upgrade or migration engine.
- A redesign of command wrappers.
- A generated layout change.
- A new dependency.
- Replacement or deletion of arbitrary files or user-authored skills.
- Prefix-based ownership inference.
- A separate migration command.
- Lifecycle record or projection updates as part of this design-document work unit.

## Naming Contract

The renderer owns an explicit mapping between the three stable command names and fixed generated skill names:

```text
session-start  -> repo-harness-session-start
session-stop   -> repo-harness-session-stop
documentation  -> repo-harness-documentation
```

All canonical and enabled runtime skill paths are derived from the fixed skill names. Command paths and command names remain stable. Wrapper content resolves the target skill through the explicit mapping above.

`project_id` remains repository identity where the product already needs it, including manifest identity and repository-specific documentation. It no longer participates in generated skill naming.

## Render Paths

### Fresh Installation

When no installed repo harness is present, render preview follows the existing additive path. The desired output set contains the three fixed skill names and their enabled runtime projections. Apply creates only the approved missing outputs.

Fresh installation does not create a migration action because there are no legacy generated skills to replace.

### Current Fixed-Name Installation

When the installed manifest and generated outputs already use the fixed names, preview uses the normal current, stale, missing, and additive classifications. No migration action is emitted solely because RH-W-0021 exists.

### Verifiable Legacy Installation

A legacy candidate exists only when the installed repo-harness manifest declares exactly the three legacy harness skills for its own `project_id`:

```text
{project_id}-session-start
{project_id}-session-stop
{project_id}-documentation
```

For each declared canonical skill and enabled runtime projection, the installed file must match the exact bytes deterministically generated for that legacy manifest and builder contract. The manifest and checker must also satisfy the existing RH-W-0024 ownership checks.

If all evidence is valid, normal render preview includes exactly one typed RH-W-0024 `migrate-generated-skills` action. That action binds:

- every exact legacy source path and source digest;
- every corresponding fixed-name destination path and destination digest;
- the manifest and checker replacements with source and destination digests;
- the exact obsolete source paths to remove.

The action is part of the content-bound approved plan and therefore contributes to `planSha256`. Apply accepts it only when the supplied plan, digest, and approval token still describe the current filesystem and desired output bytes.

## Ownership Boundary

Migration authority comes from both of these facts:

1. The installed repo-harness manifest declares the exact three legacy harness skills and their generated paths.
2. Every source file matches the exact generated bytes expected for that installed manifest.

Neither a matching name nor a `{project_id}-` prefix establishes ownership. Arbitrary user skills such as `{project_id}-release`, `{project_id}-session-start` outside the manifest-owned path set, or any other similarly prefixed skill remain untouched.

The migration mapping is closed over the exact obsolete manifest-owned skill paths. It cannot accept additional sources, destinations, replacements, or removals.

## Preview And Apply Flow

1. Render the installed legacy output model from trusted installed-manifest evidence.
2. Render the desired output model with the fixed names.
3. Build the exact old-to-new path mapping for the three harness skills and enabled runtime projections.
4. Validate ownership, exact source bytes, path containment, and unoccupied destinations.
5. Add one typed migration action to the normal action plan.
6. Calculate `planSha256` over the complete content-bound plan, including the migration action.
7. On apply, recompute the plan before mutation and reject any mismatch as stale.
8. Create and verify all destinations, replace the manifest and checker, then remove only the approved exact sources.
9. Roll back created destinations, replaced control files, and removed sources if any migration step fails.
10. Treat a fully migrated installation as idempotent and produce no further migration writes.

The existing additive writer remains responsible for fresh installations and ordinary additive actions. RH-W-0021 integrates the already bounded RH-W-0024 action into normal preview and apply rather than turning the additive writer into a general migration executor.

## Blocking Conditions

Preview must classify the migration as blocked and apply must perform no deletion when any of the following is true:

- The installed manifest or checker cannot prove ownership.
- The manifest does not declare exactly the expected three legacy harness skills.
- A legacy canonical or runtime source is missing, indirect, outside the repository, or otherwise unsafe.
- Any legacy source bytes differ from the exact generated bytes expected for the installed manifest.
- Any destination exists, including a file, directory, symlink, or reparse-point collision.
- A source, destination, replacement, or removal path fails containment or allowed-path validation.
- The approved plan, plan digest, source bytes, destination state, manifest, checker, or desired outputs changed after preview.

These checks happen before source deletion. A blocked migration cannot fall back to prefix matching, overwrite a destination, partially rename the harness, or silently use the additive path to bypass the block.

## Failure And Recovery

Migration apply retains the RH-W-0024 transaction order and rollback guarantees:

- Destinations are created exclusively and verified before sources are removed.
- Manifest and checker replacements are included in the same transaction.
- Source bytes are verified again immediately before deletion.
- Any write, verification, replacement, or deletion failure restores original source, manifest, and checker bytes and removes newly created destinations.
- A stale approved plan fails with a requirement to preview again.

The result is either the complete fixed-name installation or the original verifiable legacy installation. A mixed installation is not an accepted outcome.

## Test Design

Tests must cover the product contract rather than only this repository's current `project_id`.

| Area | Required evidence |
|---|---|
| Arbitrary project IDs | Multiple unrelated `project_id` values render the same three fixed generated skill names. |
| Fresh installation | Preview and apply remain additive and contain no migration action. |
| Legacy preview | A verifiable legacy installation yields one typed RH-W-0024 action with exact moves, replacements, removals, and digests. |
| Legacy apply | The approved migration creates fixed destinations, updates manifest and checker, and removes only exact owned legacy sources. |
| Plan digest | Adding or changing any migration field changes `planSha256`; a mismatched digest or stale plan is rejected. |
| CLI flow | Normal `render` preview and approved `render --apply` expose and execute the migration without a separate command. |
| Exact ownership | Missing manifest authority, unexpected skill sets, or modified generated bytes block before deletion. |
| Unrelated skills | Similarly prefixed and arbitrary `{project_id}-anything` skills remain byte-for-byte unchanged. |
| Unsafe state | Occupied destinations, unsafe paths, indirect paths, and changed post-preview state block without partial mutation. |
| Rollback | Injected failure at each mutating phase restores the complete legacy installation and removes partial destinations. |
| Idempotency | Reapplying after successful migration performs no migration writes and reports the fixed installation as current. |
| Commands | Command names remain `session-start`, `session-stop`, and `documentation`, and wrappers target the fixed names through explicit mapping. |
| Projection parity | Canonical source and all checked-in OpenCode and Claude projections remain byte-identical after regeneration. |

The canonical suite and repository harness parity check remain the final verification gates during implementation.

## Self-Hosted Fixture

This repository exercises the same product behavior as any generated repository. Its current project-prefixed canonical skills, runtime projections, manifest, wrappers, and documentation provide the integration fixture for the legacy path.

No other repository is known to have run the builder. The migration remains necessary as defensive compatibility, not as evidence for a broad upgrade framework.

## Alternatives Rejected

### Separate Migration Command

Rejected because users running the normal builder flow might never discover that an existing installation requires a rename. Integrating detection into normal preview makes the required action visible while retaining the existing approval boundary.

### General Migration Action In `write_outputs`

Rejected because it would expand an additive writer into a general replacement and deletion mechanism. The existing RH-W-0024 action already supplies the narrow typed transaction required by this rename.

### Prefix-Based Rename

Rejected because a prefix is not ownership evidence. It could rename or delete unrelated user skills that happen to begin with `{project_id}-`.

## Acceptance Criteria

- Every newly rendered repository uses exactly the three fixed generated skill names.
- Existing command names and command paths are unchanged.
- Command-to-skill resolution uses an explicit mapping.
- Fresh installations remain additive.
- A verifiable legacy installation receives one digest-bound typed migration action in normal preview and apply.
- Only exact manifest-owned legacy harness skills with exact generated bytes can be migrated or deleted.
- Unsafe, modified, occupied, unowned, or stale states block before deletion.
- Rollback prevents mixed old-and-new installations after failure.
- Successful migration is idempotent.
- Canonical source, tests, CLI behavior, checked-in projections, manifest output, and documentation agree on the fixed names.
- No general upgrade engine, wrapper redesign, layout change, dependency, or arbitrary replacement or deletion is introduced.
